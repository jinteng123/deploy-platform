# 原生资源发布编排与环境模型

> 2026-10-12 决策确认：继续保留现有 Deployment 与云效构建；平台负责绑定、审批、持久发布阶段、状态回读和恢复。接入/环境模型参考 Octopus，阶段编排参考 Spinnaker；蓝绿由旧稳定 Deployment、新候选 Deployment 和既有 Service selector 切换组成；精确金丝雀只接现有网关权重接口，不以副本数模拟流量，也不要求安装 Argo CRD。D1–D3 和蓝绿代码已接入，本机 Kind 覆盖成功切流、连续发布、稳定恢复及多处写入响应丢失后的重启核对；隔离非测试集群和真实用户验收仍待完成。金丝雀阈值/阶段草稿、阶段快照、网关权重执行安全骨架和操作员相邻阶段确认已实现；G1/G2 真实网关与指标适配尚未实现，审批/执行保持关闭。部署与操作步骤见[CI/CD 运营手册](./cicd-operations-runbook.md)；前端视觉是并列交付门槛，见[发布体验与前端视觉规范](./release-experience-design.md)。

## 1. 设计决定与边界（ADR）

保留云效构建、镜像仓库与现有 Kubernetes Deployment。平台管理组件绑定、逻辑环境、审批、
发布编排、状态回读和恢复，不要求业务集群安装 Argo CRD，也不把 Deployment 转换为 Rollout。
蓝绿保留旧 Deployment 承接稳定版本，另建隔离候选 Deployment；确认后切换既有生产 Service selector，
并在业务确认后更新平台活动资源引用。精确金丝雀通过已有网关的流量权重接口实现。
Argo CD、Rollouts 与 GitOps 是后续可选适配，不是当前方案的安装前提。

| 借鉴对象   | 本平台采用的设计                                         | 本期边界                                                     |
| ---------- | -------------------------------------------------------- | ------------------------------------------------------------ |
| Octopus    | 接入向导、环境与部署目标分离、同一制品逐环境晋级         | 复用逻辑环境与显式目标绑定；本期不引入 Octopus/Tentacle 或完整自动生命周期引擎 |
| Spinnaker  | 按阶段执行、人工判断、条件检查、失败恢复、可追溯执行记录 | 使用固定策略模板，不先开发任意 DAG、脚本插件市场或多组件事务 |
| Kubernetes | 原生 Deployment / Service、就绪检查、资源版本条件更新    | 不把副本数或滚动参数描述成精确流量控制                       |

Octopus 文档将逻辑环境与部署目标分开管理，并把部署步骤组织成可复用流程；本平台采用这种
对象拆分与引导方式，但目标仍显式绑定到既有集群资源。Octopus 的 Kubernetes 资源步骤示例也说明
蓝绿可由候选 Deployment 就绪后切换 Service 完成。

Spinnaker 用阶段、人工判断和前置条件编排发布；其 Canary Analysis 阶段本身只分析指标，资源准备
与清理由管线其他阶段承担。本平台借鉴持久阶段与审核体验，继续由自己的执行器管理候选和恢复，
并以现有网关权重接口实现真实流量控制。以下步骤、数据契约和恢复规则是本平台自己的定义。

[Octopus 部署流程](https://octopus.com/docs/projects/deployment-process/)、

### 本期用户路径与身份对应

```text
代码仓库（来源信息） → 云效构建 → 制品（镜像仓库 + digest + 构建/提交信息）
                                      ↓ APP_NAME 精确定位组件
业务应用 → 逻辑组件 → 环境绑定（集群 / namespace / Deployment / 容器 / 入口）
                                      ↓ 固定绑定、策略和资源基线
                          不可变发布计划 → 独立审批 → 持久阶段执行
                                      ↓ 部署、切流、观察、恢复
```

云效继续负责构建和推送；CI 事件提供构建结果与不可变制品身份。平台用 `APP_NAME`、目标集群和
完整镜像仓库校验显式绑定，不按仓库名、Deployment 名或相似字符串猜目标，也不向相似组件广播。
逻辑环境可被多个组件复用，绑定明确落到具体集群资源；测试、预发和生产沿用同一 digest 晋级。
本期逐环境创建独立计划和审批，不宣称已经具备 Octopus 式完整生命周期阶段排序或自动跨环境晋级。
生产目标由绑定和发布计划确定，构建事件不能代替生产审批。

代码仓库组件还登记仓库内构建目录。标准云效通知的 `sources[].repo` 要命中该仓库；目录为非根路径时，
流水线同时传入 `SOURCE_PATH`，平台在创建发布前逐字段校验。这样同一个 monorepo 中的多个服务可由
`APP_NAME`、仓库和目录共同区分，并在发布详情回看本次事件声明的来源。该校验用于发现接入配置错配，
通知字段仍不是签名证明，也不证明 CI 实际 checkout 或构建了对应目录与提交。

发布执行借鉴 Spinnaker 的阶段、人工判断、条件检查和可追溯运行，但阶段集合由平台策略模板约束，
不提供任意 DAG 或脚本编排：滚动更新现有 Deployment；蓝绿保留旧 Deployment，创建隔离候选
Deployment/预览 Service，检查后条件切换既有生产 Service selector；精确金丝雀由适配器调用
现有网关的权重读写/回读接口。每次外部写入前持久化动作，
写入后回读 Kubernetes 或网关事实；结果未知时保留资源锁并进入核对/恢复状态，不把请求成功等同于
流量已生效。金丝雀接口和指标契约尚未联调前，只允许策略草稿，不能提交审批或以副本数模拟权重。

减少集群内依赖仍需要资源变更与权限：创建候选 Deployment、调整 Pod 标签、管理专属 Service、
更新已授权的网关路由。接入核对页逐项预览这些影响，未经显式绑定不自动猜测或接管资源。
平台承担原先由渐进控制器承担的状态管理、观察与恢复责任，必须先通过故障演练再开放生产。

## 2. 用户结果与验证

- 研发能沿着“代码仓库 → 镜像仓库 → 组件 → 环境 → 容器”说明一次构建会更新哪里。
- 运维能在接入时判断哪些策略可用，并看到缺失条件和修复入口。
- 审批人能判断本次变更、影响流量、验证证据和恢复目标；批准后不因绑定变化更新别的资源。
- 发布操作者能区分正在部署、等待确认、流量已配置、业务已验证和状态未知，并找到下一步。

用户对绑定困难、内网 CI 接入和前端美观的反馈已成立；真实网关能力、双版本兼容性、容量开销、
指标质量以及界面可用性尚未验证。试点邀请 5 位真实操作者完成接入、申请、暂停和恢复，目标至少
4 位不依赖口头解释即可判断目标与下一步；记录求助点、耗时和误操作，未达目标先改体验。可直接执行的
[可用性验证手册](./usability-validation.md)规定任务卡、隔离环境、记录项与复测门槛。
维护成本包括双版本容量、网关适配、平台值班和每月恢复演练，不以“不装 CRD”推定没有运维成本。

## 3. 应用、组件、环境与目标

| 对象     | 含义与关键字段                                                                         | 约束                                                         |
| -------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 应用     | 用户理解的业务分组，例如“订单系统”                                                     | 不直接充当 Kubernetes 资源名                                 |
| 组件     | 独立构建/发布的单元，如 orders-api；代码地址、目录、镜像仓库                           | 第三方镜像可无代码来源，镜像仓库必须明确                     |
| 环境     | 测试、预发、生产等逻辑环境；发布策略、审批规则                                         | 环境不是集群，一个环境可有多个显式目标                       |
| 环境绑定 | 组件 + 环境 + 目标；集群、namespace、容器、模板资源及流量绑定，可保存 `strategy_draft` | 一个发布任务对应一个具体绑定，多目标结果独立；草稿不参与执行 |
| 制品     | repository + digest，附 tag、构建与提交来源                                            | 同一制品晋级，不重新解析 tag、不重新构建                     |
| 发布计划 | 制品、绑定版本、资源基线、策略步骤、检查与恢复条件的不可变快照                         | 改计划重新预览、申请审批                                     |
| 执行     | 持久阶段、动作、观察记录、操作者与恢复记录                                             | 事实不由前端缓存或日志字符串推断                             |

现有 `apps` 行实际代表一个部署绑定，`(cluster_id, app_name)` 及 Runner 的 `app_id` 保持兼容。
新增逻辑应用/组件/环境及绑定关联，不能把现有集群 ID 直接解释为环境 ID。旧 `env_code` 仅作迁移
提示，由管理员核对逻辑环境归属，不自动合并同名组件或猜测跨集群关系。缺失来源继续标为缺失。
迁移 010 建立逻辑应用/组件/环境/绑定表及可空的策略草稿字段；迁移 011 增加只读发布计划快照表，001–010 保持既有内容。

环境分类不能削弱旧生产保护：实际目标集群或逻辑环境任一被标为生产，都执行生产门禁；
属性冲突先阻断并要求管理员核对，不能通过重命名环境让 Runner 自动发布到既有生产目标。
Runner 自动授权同时要求环境与实际目标符合非生产策略，修改归属后重新校验并使旧计划失效。

每个绑定区分 `template_workload_ref`（模板/最初资源）与 `active_workload_ref`（当前承接流量资源），
资源引用含 cluster、namespace、kind、name、UID 与最近观察的 resourceVersion。迁移 018 为旧绑定
回填可确认的位置/名字，但 UID 保持未知；第一次创建发布计划时读取 Kubernetes 实际 UID 并固定。
蓝绿成功后活动资源可变，模板名不能被当成当前生产版本；成功确认在同一个数据库事务里更新活动
Deployment 名、UID 和运行终态。后续计划比对活动 UID，同名资源重建视为新资源并阻断发布。operator/admin
可从环境页显式重新核对：服务端读取当前 Deployment 并验证绑定目标，检查相关资源锁后仅更新活动引用；
不修改集群资源，活动发布锁存在时拒绝。重新核对不修改初始模板引用，也不能通过普通草稿绕过身份冲突。

### 引导：先建立关系，再选择策略

1. 选择/创建业务应用，命名组件，登记代码来源或明确选择第三方镜像。
2. 填镜像仓库，从真实集群选择 namespace、Deployment、容器；只读回读当前镜像。
3. 选择逻辑环境，核对生产属性与审批；添加其他环境时复用组件，不复制含糊的名称。
4. 选择策略。滚动只需工作负载；蓝绿需要显式 Service；金丝雀需要稳定/候选后端及网关路由。
5. 能力检查展示“可用 / 缺配置 / 不支持 / 无法确认”和影响预览；未通过只能保存草稿。
6. 核对关系，保存绑定，再接云效 Runner；接入测试不会触发发布。后续配置页可重新检查。

代码未登记、镜像未绑定、部署目标无效、发布策略未配置分别显示，不能用一个“待补全”混合表达。
构建只上报该组件的不可变制品；目标由授权确定，策略来自受控环境绑定。

## 4. 策略能力与接管条件

| 策略       | 执行方式                                                   | 生效时点                            | 必备条件                                       |
| ---------- | ---------------------------------------------------------- | ----------------------------------- | ---------------------------------------------- |
| 滚动       | 更新当前 Deployment 镜像并等待 rollout                     | 新 Pod 就绪后逐步承接流量           | 沿用现有审批、制品与目标校验                   |
| 蓝绿       | 新建候选 Deployment，验证后修改明确绑定的 Service selector | 切换 Service 后新连接逐步到候选版本 | 候选隔离、双份容量、Service 写权限、双版本兼容 |
| 加权金丝雀 | 两套 Deployment/Service，按计划设置网关后端权重            | 网关配置生效后按其规则分流          | 既有网关权重读写、路由归属、指标、稳定版本容量 |

首期蓝绿/金丝雀只支持无状态 HTTP 服务、单容器镜像变更、一个明确流量入口；不接 StatefulSet、
独占卷、自动迁移数据库的启动任务、队列消费者或共享入口的多组件联动。关联 HPA 的目标先判为
不支持，直到扩缩容与双版本容量方案验收。多入口即使共用一个 Deployment 也不能假装一次原子切换。
这些限制通过后端能力校验和前端说明共同执行，不能仅靠禁用按钮。

管理员授予 namespace 内必要的 Deployment / Service / Pod / EndpointSlice 读写权限及限定网关路由
权限；不要求集群管理员全权限。生产通用改镜像、扩缩容、重启、删除和 YAML 入口继续受保护；
只有绑定审批计划的执行器能操作计划内资源，不能把这条内部路径暴露成机器授权绕过入口。

## 5. 蓝绿执行与恢复

### 5.1 首次接入与候选隔离

预览所有会选择当前 Pod 的 Service 和已知路由；额外入口无法排除时阻断启用并要求核对。
已有 Service 只按通用 app 标签选 Pod 时，直接复制标签会让候选提前接流量，因此必须先在一个
获批的接管计划中建立版本隔离：给当前 Pod 模板添加稳定版本标签、等待就绪，再以条件更新收窄
Service selector 并回读 EndpointSlice，确认仍只指向稳定版本。预览说明这可能引发一次模板滚动。
原 Deployment 的不可变 selector 不改写，新增资源拥有独立且互不匹配的 selector；先做匹配冲突
检查，无法满足则拒绝接入。不能只追加候选版本标签却复制所有通用标签：候选 Pod 也不得匹配
旧 Deployment/ReplicaSet 的 selector。必要的标签调整逐项预览，影响既有监控/网络策略时先解决
兼容性。标签命名、所有权范围与接管基线记录在计划中。

### 5.2 固定步骤

1. 校验批准计划、目标 UID、selector、镜像、配置摘要、容量和稳定版本健康；领取共享锁。
2. 以执行 ID 派生唯一候选名称，创建独立 Deployment，使用固定 digest；不改原 Deployment 镜像。
   清除模板中的服务端元数据，不复制旧 ownerReferences；不生成或快照明文 Secret。
3. 等待候选就绪，回读容器镜像与端点；用隔离的预览 Service 做业务检查。就绪不等于业务通过。
4. 进入“等待切换确认”，展示证据、稳定版本和恢复窗口；本期生产默认人工确认，不新增未批准步骤。
5. 检查 Service UID / resourceVersion / selector 与计划一致，条件更新 selector，回读确认。
   冲突停止；网络超时记结果未知，先读实际状态，不能直接重复切换或宣称失败。
6. 观测新版本业务指标和端点，满足窗口后记发布成功并更新活动资源。旧版本保留供恢复。
7. 蓝绿计划快照固定 24 小时的候选保留期；稳定版本恢复满期后，操作员可显式清理候选。清理失败记入运行事件并显示告警，不伪造发布成功，也不删除稳定 Deployment。

Service selector 更新和节点数据面收敛不是同一个瞬间；长连接可能继续留在旧 Pod。
界面显示已配置入口、端点观察与业务验证分别完成，不能承诺切换即所有请求迁移或绝对零中断。
原资源原理见 [Kubernetes Service](https://kubernetes.io/docs/concepts/services-networking/service/)。

### 5.3 恢复与资源生命周期

切换前失败：保持稳定入口，候选标记失败并按保留策略处理。切换后失败：确认旧版本有足够就绪
容量且兼容，条件恢复 Service selector，再回读端点并做业务检查；业务恢复才记恢复完成。
稳定版本不健康或入口被外部改动时进入“需要处理”，不得盲目把用户流量导回。

回退只将生产 Service 指回稳定 Deployment，不回滚数据库迁移、ConfigMap/Secret 或 Helm/Git 配置。共享配置变动可能使旧版本无法恢复；发布前必须记录版本引用/摘要及兼容性声明。无法证明兼容时选向前修复。`restore_stable` 和蓝绿 `cancel` 都要求 operator/admin 在确认弹窗明确勾选“稳定版本兼容当前数据库与配置”；请求缺少该确认时，服务端在任何 Kubernetes 读取/写入前拒绝，确认事实写入运行事件和审计记录。该勾选是操作员声明，不是平台自动兼容性证明。
候选保留期限（当前默认为 24 小时）写入不可变审批计划，缺少有效策略时拒绝清理。候选回收仅在
运行已恢复稳定版本后开放，并重新验证稳定入口 selector、应用绑定、候选 UID 与平台所有权标签；
清理期间通过有期限的多资源锁隔离并发发布，结果不明时租约到期前保持锁定。回收顺序为候选预览
Service、候选 Deployment；原有用户 Deployment 和已成为活动版本的候选永不由此入口删除。
原有资源的长期保留/退役由管理员显式制定，不靠命名后缀推断所有权。

### 5.4 完整配置恢复的后续实现边界

当前恢复只负责镜像 digest 和蓝绿 Service 入口，不回放 Kubernetes manifest。发布计划继续固定部署配置仓库、目录和 Runner 实际检查的完整 Git commit；它是恢复配置的输入依据，不是平台已保存或已应用配置的证明。ConfigMap/Secret 的 UID/resourceVersion 只能检测变更，不能还原内容。平台不把 Secret 或 ConfigMap 值写入计划、审计和通知；Kubernetes RBAC 的 `get secrets` 即使协商 PartialObjectMetadata，权限本身仍能读取完整 Secret，因此不能把“只要元数据”当作数据隔离。现有单一 `CREDENTIAL_ENCRYPTION_KEY` 也没有密钥版本/轮换方案，不能直接扩展成长期配置快照密钥。

A5 配置恢复应按已固定的 Git revision 重跑独立登记的 Yunxiao 部署流水线，而不是默认重跑镜像构建流水线。每个发布目标需单独绑定配置部署流水线；审批计划固定流水线连接/ID、`DEPLOY_CONFIG_REVISION`、不可变 `IMAGE_FULL` digest 与目标环境。经审批后通过 Yunxiao [CreatePipelineRun](https://help.aliyun.com/zh/yunxiao/developer-reference/createpipelinerun) 触发，并持久化 Yunxiao run ID、幂等键和输入快照；运行结束必须核对流水线报告的配置 commit、镜像 digest 和目标，再记录结果。触发失败、状态未知或回报不匹配时不得宣称恢复成功。无法在目标流水线验证精确 commit checkout 时，仍走人工恢复并向前修复。

这条配置恢复链尚未实现。它需要独立的环境级流水线绑定、审批后的触发/状态跟踪和完成回报契约；不会因为当前 release 已记录 commit 就自动执行配置。数据库迁移是否可逆仍需应用级兼容策略，平台不承诺自动回滚数据库。

计划详情提供配置恢复流水线的固定输入只读映射，便于操作员核对稳定 commit、由稳定仓库与 digest 构成的完整不可变镜像引用，以及目标工作负载。流水线元数据连通性检查和参数预览都不能证明流水线写入范围；接线前还须定义它是仅应用配置，还是会改写 Deployment/镜像，并确认候选与稳定工作负载的目标语义。当前平台蓝绿执行器会创建隔离候选 Deployment，而绑定只快照逻辑目标 Deployment；责任和目标尚未确认时，保持配置流水线触发关闭，避免两个执行器并发改写同一工作负载。

2026-10-15，操作者确认目前也不清楚该流水线究竟只改 ConfigMap/Secret，还是会同时改 Deployment/镜像。因此，环境页将此显示为“写入范围尚未确认”，仅允许登记连接和流水线 ID；元数据检查不代表权限/写入范围审计。为帮助定位，环境页增加“分析可能写入范围”：服务端只读调用云效 `GetPipeline`，在服务端解析 YAML 并返回结构节点引用、固定风险标签和定义 SHA-256，不返回原始 YAML、命令或参数；它可能标记 Kubernetes、Helm、基础设施写操作及不透明脚本/模板。缺定义、过大或无法解析时不会判为只读，所有结果均要求人工复核。展开式核对指南按“完整定义、动态命令、执行身份/权限、与发布 Worker 的写入边界”提示操作者检查。迁移 035 现将人工结论以追加方式绑定流水线定义指纹，记录核对人和时间，并由环境模型返回每个绑定的最新记录；当前流水线或定义变化时旧记录显示为过期。该结论只作审计，不是自动安全证明、审批凭据或触发许可。静态扫描不能展开引用模板、下载脚本、动态变量、插件或真实授权范围，所以不能据此开启执行。接入前仍需核实实际任务、资源类型、namespace、工作负载范围、绑定外影响及执行身份，并定义与平台镜像/蓝绿 Worker 的互斥和职责边界。核实完成之前，审批触发、run 跟踪和稳定配置自动恢复不得接线。接口依据：[云效 `GetPipeline` 官方文档](https://help.aliyun.com/zh/yunxiao/developer-reference/getpipeline-get-pipeline-details)。

为减少环境绑定时人工查找流水线 ID，operator/admin 现在可通过云效只读 `ListPipelines` 按名称搜索并分页选择，再读取所选流水线元数据；也保留高级手工 ID。该改进只完成“连接到目标流水线”的引导，不改变上述执行器所有权门槛。

### 6.2 阶段计划与指标

示例计划 `5% → 20% → 50% → 100%` 仅用于说明；实际候选权重和各阶段最短观察时长、最小请求数、错误率/延迟
阈值、基线比较和人工确认点由服务负责人配置并纳入审批，不作为默认生产放量策略。计划必须配置 2–10 个
严格递增的阶段，最后一个阶段为 100%；每个阶段都要先达到观察时长与指标条件，再由操作员确认下一步。
100% 阶段仍须完成观察与人工确认后才能记为成功。每一步先校验目标 → 设置权重 → 回读生效 → 等待观测窗口 →
判断指标 → 确认/继续。

阶段确认使用发布运行控制入口 `POST /api/v1/delivery-runs/:id/actions` 的
`confirm_canary_stage` 动作，并要求 operator/admin、当前运行版本和幂等键。服务端只接受健康且等待确认的
最新阶段快照，一次只创建计划中的下一阶段 `awaiting_weights` 检查点；最终 100% 阶段确认后才结束运行。
确认人、确认时间和已确认阶段随事件持久化，重放相同幂等键不会重复推进。此控制动作本身不写网关，实际阶段
执行仍须经过“写前动作意图 → 网关条件写入 → 有效权重回读 → 指标观测”，计划审批和执行门禁在 G1/G2
集成完成前保持关闭。

策略向导首次选择金丝雀时显示两张空白阶段卡，帮助操作者看见最低阶段数；比例和时长仍由服务负责人填写。
长配置弹窗固定标题与底部操作区，正文独立滚动；阈值或阶段缺失时，禁用保存旁显示可执行的补全提示。
该表单只保存草稿，未完成真实网关与指标联调前不能申请审批或调整流量。

“精确”指可配置后端权重，不保证任意短窗口恰好同等比例的请求；长连接、会话黏性和样本量会影响
实际分布。页面同时展示计划权重、已生效配置与实际请求占比，后者附时间窗口/请求数/来源。

### 6.3 指标判定核心（基础实现）

服务层已新增纯函数指标判定核心：调用方必须显式提供最小请求数、观测最大年龄、候选错误率上限、相对稳定版本的错误率差值上限、候选 P95 延迟上限和 P95 相对增幅上限；策略还固定 2–10 个严格递增的候选流量阶段、各阶段观察时长及最终 100% 检查点。不读取平台默认放量比例或阈值。稳定与候选样本按 digest 分开核验，并要求完整窗口、有效时间戳、足够样本、健康稳定基线和两版本 P95 数据。

数据缺失、digest 不匹配、窗口未来/过期、样本不足、基线不健康或指标无效时结果为 `pause`；候选健康状态降级或指标越界时结果为 `restore_recommended`；数据健康且处于阈值内时结果仍为 `awaiting_confirmation`。`EvaluateCanaryStageObservation` 还会核对网关回读的稳定/候选权重是否恰好符合当前阶段、阶段最短时长是否已过，以及完整指标窗口是否从该阶段生效后开始并覆盖配置时长。判定只提供建议，不调网关、不自动放量或恢复。阈值与阶段现纳入不可变策略版本和计划快照（迁移 022 的 JSON，无需新增列）；计划快照 schema v4 固定稳定版和候选版 digest，无法解析时阻断金丝雀计划。当前没有实际网关/指标 provider、API/Worker 或生产任务调用这些服务，因此不代表 G2 已接通，金丝雀仍不可审批或执行。

阶段观测新增厂商无关 `CanaryMetricsAdapter` 边界：请求从固定的阶段开始时间和路由出发，只查询计划中固定的两个 digest；调用前后会回读路由，权重/revision 改变则进入 `needs_attention`。窗口未覆盖配置时长则保持 `observing`；完整健康结果被持久化为 schema v2 快照，包含 `evaluated_at`，回放按该时刻复算。schema v1 仍可读取，旧快照用其 `observed_at` 作为兼容判定时刻。人工确认会重新检查观测时间和判定时间是否在策略新鲜度范围内。前端阶段卡将采样时刻与判定时刻分开展示。以上仍是服务层接口及测试实现，真实指标厂商接入、后台调度和故障恢复写入仍待完成。

2026-10-13 新增厂商无关的阶段权重写入服务骨架：先将动作意图写入外部动作日志，再以路由修订号条件更新并回读有效权重；即使写入响应丢失，也以回读决定 applied、not_applied 或 unknown。阶段快照写入进一步要求对应阶段存在匹配的 applied 动作、目标比例、路由身份、回读权重及阶段开始时间，并校验只能发生允许的相邻阶段转换，避免调用方仅构造 JSON 就伪造“已生效”阶段。该骨架尚未连接实际网关、真实指标源、候选后端准备和操作员控制 API；G1/G2 接入门禁保持关闭。

稳定流量恢复现在也有服务层原语 `RestoreCanaryStageStable`：它只从最近一次已生效的阶段动作取得路由身份，写外部动作前持久化恢复意图，再以当前 revision 条件设置稳定版 100%、候选版 0%，并强制回读。写入响应丢失时以有效路由状态判定是否已经恢复；路由权重漂移或状态未知时不会覆盖外部改动，也不会盲目重复写入。恢复成功只会把运行转入 `awaiting_restore_verification`，保留运行锁并等待业务验证，既不会宣告发布成功，也不会自动释放资源。

阶段确认后、下一档权重尚未写入时，最新快照是 `awaiting_weights`，没有当前阶段的权重回读。如果下一阶段动作已持久化为 `applied`、但进程在追加观察快照前退出，恢复从该动作回读重建当前阶段证据；否则使用紧邻上一阶段的健康确认快照和对应 `applied` 动作观测。实时读取仍须匹配已记录的路由身份，权重只能等于最后一个可由 `applied` 动作证明的回读或已是稳定版 100/0，随后通过当前 revision 条件恢复。若权重已经外部漂移，则保持运行锁并进入 `needs_attention`。阶段边界、动作与快照间崩溃窗口及漂移拒绝均有回归测试。

这仍是未接入真实网关 adapter、Worker 的服务层能力：操作员尚不能通过 API 触发这次网关恢复，金丝雀审批与执行继续关闭。恢复后的业务验证确认已接入会话控制 API：只有运行仍处于 `awaiting_restore_verification` 且存在通过计划 digest 校验的 100/0 回读快照时，operator/admin 才能提交 `confirm_canary_restore`；服务端记录操作者和时间，将本次候选发布标记为失败终态并原子释放资源锁。指标失败、未恢复、路由未知或没有恢复回读快照时均不能走此确认动作。运行详情新增恢复结果卡和确认对话框；确认后卡片改为业务验证完成态，时间线显示操作员审计记录。手机视口浅/深色视觉测试检查无横向溢出和至少 4.5:1 的文字对比度，深色告警采用固定深色文字配浅琥珀底色，避免主题切换时出现低对比度。

## 7. 持久编排、权限与崩溃恢复

MySQL 保存不可变计划、审批、执行、步骤、动作意图、观察值和事件。内存只作派生缓存。
绑定版本、制品、工作负载/入口 UID、网关路由修订、步骤、指标、恢复目标和保留规则都进入审批
指纹；基线变更需要重新申请。人类独立审批规则不因策略改变，机器密钥不得批准、扩大流量或任意选目标。

锁覆盖环境绑定、模板/活动/候选工作负载与流量入口；同一 Service/网关路由的别名共享冲突范围。
多资源锁在数据库事务中按稳定顺序领取，全有或全无。现有滚动、回退、Runner 和 Kubernetes 写
入口也查询该归属索引；存在未纳入保护的入口时不启用新策略。一个入口不能被多个绑定独立接管。

当前开发进展（2026-10-09）：蓝绿候选准备使用计划 ID 固定候选 Deployment/预览 Service 名称，动作所有权按运行任务记录。执行前重读 Deployment、Service UID/config hash、镜像与隔离 selector；候选创建后检查 rollout、desired/ready/updated/available 副本、EndpointSlice 和 ReplicaSet owner UID。稳定 Service selector 先条件切换到稳定轨道，再以旧 selector、resourceVersion 和身份校验条件切至候选或恢复稳定；请求结果不明时先回读，不盲目重放。

蓝绿计划可走独立人工审批。人工预检确认会记入审批审计；审批时重新核对计划快照并一次性申请多资源锁。批准后执行候选准备，停在 `awaiting_candidate_review` 等待操作员确认切流。运行详情由 `GET /api/v1/delivery-runs/:id` 和 `GET /api/v1/delivery-runs/by-deploy-log/:id` 读取；前端通过 `POST /api/v1/delivery-runs/:id/actions` 提交 `confirm_cutover`、`confirm_live_verification`、`restore_stable`、`reconcile`、`cleanup_candidate`，每次带 `expected_version` 与 `idempotency_key`。服务端仅允许 operator/admin，且重新检查候选、生产 Service selector 和端点。切流后进入 `awaiting_live_verification`；业务确认时再次读取健康与 EndpointSlice，再更新应用活动 Deployment 绑定并完成运行。恢复会把入口指回稳定标签，运行 status 记为 failed、stage 记为 `restored`；候选按审批快照保留 24 小时，之后 operator/admin 可提交 `cleanup_candidate`。清理使用 UID 前置条件、平台/计划/运行所有权标签、稳定绑定与入口回读，并按预览 Service 再候选 Deployment 的顺序删除；期间使用 15 分钟可过期资源租约，避免进程中断永久占锁。Kubernetes 前台删除可能先返回“仍在终止”；此时平台保留租约并报告待核对，之后读回 NotFound 才完成该删除动作。EndpointSlice 控制器短暂保留旧稳定端点时，服务端等待其收敛；不收敛转 `needs_attention` 并保留活动运行资源锁。

启动恢复时，没有未决外部动作的两个人工关口运行保留阶段/锁；若关口存在 `intent` / `unknown` 外部动作（例如 Service PATCH 可能已生效但响应未记录），则转 `needs_attention` 并保留锁。操作员核对集群后才能恢复流程；服务不会盲目重放候选创建或 Service 切换。蓝绿 `reconcile` 先回读并验证生产 Service 身份、配置和 selector：仍指向稳定版本时，按持久化动作记录续接候选准备，允许采用已创建的候选 Deployment 并补建缺失的私有预览 Service；已指向候选轨道时，必须先完整核验候选 Deployment、预览 Service 和端点，再核对切流动作。selector 指向未知轨道时停止并转 `needs_attention`。2026-10-10 本机 Kind E2E 通过 TLS 故障代理实测候选 Deployment POST、候选预览 Service POST 和生产 Service PATCH 三个写入响应丢失并分别强制重启后端；reconcile 保留已创建的 Deployment UID，补建或读回预览 Service，并通过真实入口回读核对切流动作。启动恢复事件键包含运行版本，确保同一发布多次经历故障和操作员恢复时不会复用旧事件键。fake Kubernetes 回归测试也覆盖候选部分创建后的恢复且不重复创建 Deployment。其它真实写入点和非测试集群故障仍需单独验证。滚动任务仍提供 `/api/v1/deploy/logs/:id/reconcile`，仅当 Deployment 实际镜像等于批准目标时才继续 rollout 核验。

2026-10-10 本机 Kind E2E 还覆盖候选资源清理的真实响应丢失：Service 删除已被 API Server 接受、后端在收到响应前强制退出；重启后清理重读并确认 Service 已不存在，再删除候选 Deployment。若 Deployment 尚在前台终止，平台返回冲突并保留租约；待 Kubernetes 删除完成、隔离测试数据库中的租约到期且后端重启后，下一次清理通过 NotFound 回读完成动作。测试验证稳定 Deployment UID、活动绑定、稳定 Service selector 与 EndpointSlice 均未改变。此外，`restore_stable` 的真实 Service selector PATCH 成功后响应被丢弃并强制重启；重启将运行置于 `needs_attention` 并保留锁，operator 重试从 live selector 确认原动作 applied 后再终止运行。该过程发现并修正 `restore_stable` 两处状态缺口：终态 status 应为 failed、stage 应为 `restored`；如果 selector 已经稳定，还必须读取并完成之前的动作 intent，避免结束运行时留下未决 journal。

- 暂停：蓝绿在两个操作员关口暂停平台推进并保留锁，不改入口；切流前稳定版承接流量，切流后候选版继续承接流量。滚动只允许在 `rollout_wait` 暂停平台后续健康检查，Deployment 控制器仍会继续替换 Pod，暂停不等于停止 rollout 或回切流量。金丝雀只允许在健康观测完成、等待人工确认的关口暂停；阶段快照和资源锁保留，不触碰网关。
- 继续：蓝绿只解除关口暂停，仍停在原关口等待人工确认；滚动将任务重新排队，回读已记录的镜像动作并继续 rollout/镜像核对。金丝雀继续后仍停在原健康确认关口，提交阶段确认前重新校验观测时效；暂停/继续不调权重、不自动扩大流量。真实网关恢复 API/Worker 和阶段执行调度仍待 G1/G2 联调。
- 取消：蓝绿仅开放于操作员关口；服务端先重新核对并恢复生产 Service 到稳定版本，再标记已取消、释放锁并保留候选供排查。滚动只允许在镜像写入前、且不存在 `set-image` 动作时取消，标记终态并释放锁；镜像动作创建后需提交显式镜像回退。金丝雀只允许在首次外部动作前取消：任务可以仍在排队，也可以已被 Worker 领取；事务锁定任务行并核对没有任何外部动作记录，再将任务标记为失败、运行标记为已取消、撤销 claim 并释放资源锁。Worker 外部动作 intent 与取消竞争同一任务行锁：动作先记录则拒绝取消；取消先提交则旧 Worker claim 被 fencing，后续检查点和动作写入都会失败。已有外部动作时必须先由真实网关适配器核对/恢复稳定流量；此后的完整取消链仍待 G1/G2 联调。未知状态仍须先核对。
- 恢复：按批准恢复目标执行；超时/未知结果先读回，不等于“重试整个流水线”。
- 平台离线：现有 Deployment 与已配置路由继续工作，但没有新增平台检查和自动放量；UI 显示数据过期。
- 平台重启：先恢复持久任务并回读实际镜像、端点与路由，默认暂停等待核对；不自动扩大、清理或直接
  重放最后一次切换。稳定状态明确且仍符合计划后，操作者继续；漂移、未知或不兼容进入需要处理。
