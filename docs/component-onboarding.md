# 组件接入与镜像对应关系

## 平台现在如何建立对应关系

先确认至少一个 Kubernetes 集群已接入并启用；向导必须从该集群读取现有 Deployment 和容器。若没有可用集群，「接入组件」暂不可用，管理员可从空状态直达「集群设置」完成前置配置；operator 需联系管理员。

打开「应用与组件 → 接入组件」，按三个步骤设置：

1. **组件与代码来源**：给一个可独立更新的服务填写组件标识，例如 `order-api`。
   代码仓库用 HTTPS 主页地址，单仓多服务通过构建目录区分，如 `services/api`、`services/web`。
   第三方镜像可以不登记代码仓库。当前平台记录这些信息，不会克隆仓库、配置仓库凭据或执行构建。
2. **镜像与部署目标**：选择已经接入的集群、namespace、现有 Deployment、容器。
   平台读取资源，单容器 Deployment 自动选择容器，多容器要求选择具体目标。
   镜像仓库可从当前容器带入，也可填写 CI 实际 push 的完整路径，例如 `registry.example.com/orders/api`。
   不填协议、tag 或 digest；CI 每次报告完整版本和 digest。
3. **核对与接入 CI**：平台只读检查目标仍存在，展示当前镜像和完整对应关系。
   用云效全局参数 `APP_NAME`、`TARGET_CLUSTER`、`IMAGE_FULL` 模拟一条构建通知；登记代码仓库时再核对 `sources[].repo`，登记非根构建目录时还需匹配 `SOURCE_PATH`。任一字段不匹配都会说明应填值并阻止保存。模拟在浏览器本地完成，不发送 webhook、不创建发布任务。
   确认后保存绑定，保存时再次读取目标容器，保存本身不会更新镜像。
   保存成功提示中的「关联业务应用与环境」会携带刚保存的部署目标，直接打开环境配置；再选择业务应用、逻辑组件和环境，发布策略会和这组关系一起保存。平台不会按名称猜逻辑归属。

组件列表会把业务应用/发布组件/逻辑环境与集群/namespace/Deployment/容器并排展示。页面上的映射示例强调：CI 的 `APP_NAME` 定位组件，镜像仓库全路径必须与绑定完全一致，digest 只固定本次构建出的镜像版本；命中后只更新这条绑定指定的容器。桌面用表格查看多组件，窄屏改为逐个目标的关系卡片。

### 把部署配置仓库绑定到组件

代码仓库和部署配置仓库分开登记。代码仓库表示源码从哪里构建；可选的「Helm / Git 部署配置仓库」表示该组件使用的 values、chart 或部署清单来源。填写仓库和仓库内目录后，保存的组件绑定会固定这组关系；一个仓库里有多个服务时，可以用不同目录分别对应多个组件。

若目标环境属于同一个逻辑组件，各环境绑定应登记相同的部署配置仓库和目录。平台在保存环境关系时检查这一致性，避免同一个逻辑组件在测试和生产指向不同配置来源。平台不会读取或克隆仓库，也不会替 CI 执行 Helm 渲染或配置应用。

### 配置部署流水线的写入范围

环境绑定可以登记独立的 Yunxiao 配置部署流水线，并只读检查连接、名称、类型和更新时间。另有“分析可能写入范围”操作，会通过 Yunxiao `GetPipeline` 读取流水线定义，在服务端静态检查 YAML，只返回节点位置、固定风险分类和定义 SHA-256；原始 YAML、命令、任务参数和凭据不会返回浏览器。定义指纹提供完整 SHA-256 复制操作。分析可能标记 `kubectl`/`oc` 写命令、Helm/基础设施变更命令、ConfigMap/Secret 或工作负载相关步骤，以及无法展开的脚本/模板。云效定义缺失、过大或无法解析时不会判为只读。此分析只是定位线索，不能证明完整写入范围，也不能替代权限核对；当前真实范围仍未确认，可能只更新 ConfigMap/Secret，也可能同时创建或更新 Deployment、镜像或其他资源。展开“在云效完成 4 项核对”可依次检查完整定义、动态命令、执行身份/权限及与平台 Worker 的写入边界，并记录定义指纹、节点、身份与目标。页面始终要求人工复核；登记或分析都不会运行流水线，也不会接入平台发布 Worker。

审批后触发和配置恢复接线前，仍须在云效核对完整流水线、被引用的模板/脚本/插件、动态下载内容和实际执行身份，确认资源类型、namespace、目标工作负载、绑定外影响范围及身份权限。再明确配置流水线与平台镜像/蓝绿执行器的写入责任，避免同一 Deployment 或镜像被两条链路并发修改。将人工核对结果保存为接入契约和验收记录；在此之前，配置流水线运行触发、运行跟踪、自动恢复和与蓝绿的联动均保持关闭。`GetPipeline` 返回流水线定义的依据见[云效官方文档](https://help.aliyun.com/zh/yunxiao/developer-reference/getpipeline-get-pipeline-details)。

组件关联 Runner 后，生成脚本会从绑定读取固定仓库/目录，并在上报镜像前核对 CI checkout 的 Git `origin`、登记目录和 `HEAD`。默认检查通知任务当前目录；配置仓库单独 checkout 时可设置 `DEPLOY_CONFIG_WORKDIR`。登记目录须属于当前 commit，且没有已修改、未跟踪或忽略文件。校验通过后脚本自动读取完整 commit SHA 并把来源记到同一个镜像 release；流水线继续提供旧的 `DEPLOY_CONFIG_REVISION` 时，它必须与实际 HEAD 一致。脚本拒绝流水线用 `DEPLOY_CONFIG_REPOSITORY` 或 `DEPLOY_CONFIG_PATH` 覆盖组件登记值。云效构建任务仍需自行 checkout、渲染 Helm 并执行已有部署步骤；Git checkout 校验不能证明 Helm 渲染结果或配置已在集群生效。

发布详情会分别显示组件登记的部署配置仓库/目录和本次 Runner 报告的仓库/目录/完整 commit。绑定了固定配置仓库却未上报 commit 时，会明确显示“尚未固定 Git commit”；来源与绑定相符时标记“配置仓库与目录已匹配”；仓库/目录与绑定不一致时展示警示。没有固定配置仓库的旧集成仍可查看本次上报值，但不会显示为已验证匹配。

还没有登记组件配置仓库时，旧式按构建传入 `DEPLOY_CONFIG_REPOSITORY`、`DEPLOY_CONFIG_PATH`、`DEPLOY_CONFIG_REVISION` 的方式仍可用。若此次实际使用 Helm/Git 配置却没有上报 revision，计划会显示未知并要求人工确认；若组件已经固定配置仓库但 Runner checkout 校验或来源报告失败，则阻断创建计划，修复后需重新上报并生成计划。

第二步选定容器和镜像仓库后，向导会在视口内展示持续更新的关系图：`APP_NAME + TARGET_CLUSTER → 精确镜像仓库 → 集群 / namespace / Deployment / 容器`。镜像 tag 与 digest 由每次构建事件提供。该预览用于在保存前确认 CI 会命中哪里，不表示已保存，也不会改动集群；最终核对页仍要求操作者再次确认完整关系。

目标选择后还会只读检查 Deployment 的 Pod 标签、匹配的 Service selector 和指向该 Deployment 的 HPA。
检查失败显示为“无法确认”；它不证明 Ingress/外部网关、写权限、候选隔离或双版本容量已就绪。
蓝绿计划现已支持独立审批、候选 Deployment/预览 Service、Service 条件切换、业务确认、稳定版本恢复和恢复后候选清理；工作负载绑定会分别记录最初模板与当前活动 Deployment 的 UID，业务确认后原子推进活动引用。接入还包括版本化策略历史：策略调整会追加版本，计划快照固定创建时的版本和蓝绿候选保留小时数。镜像漂移按需读取并保存当前状态和状态变化历史。Runner 可为自身制品追加绑定专属 CI / Smoke 证据及仅报告的扫描记录；平台从制品固定 digest 和 `runner:<接入ID>` 身份。线上事件可记录故障发生、开始干预及业务恢复时间，可显式判定关联部署是否导致故障，并追加修复类型、计划内/外状态和同一生产应用的修复部署关联。operator 的生产审批按逻辑应用与生产环境授权，可在「设置 → 发布审批范围」中配置；新迁移不会自动给现有 operator 授权。启用前仍须应用迁移 010–038，并在隔离集群完成真实验证。网关金丝雀目前只保存为等待联调的策略草稿，缺少现有网关接口契约时不能申请执行，也不能退化为滚动发布。

接入前需已有工作负载和集群读取权限。当前执行对象为 Deployment，不将 StatefulSet、Job、数据库等展示为可直接接入的镜像发布目标。

### 目标集群权限与身份

集群设置里保存的 kubeconfig/token（或 SSH 连接所用的集群身份）是发布 Worker 的执行凭据。它需要在目标 namespace 内执行滚动更新；蓝绿还需要创建、条件修改和清理 Deployment/Service。Helm 的 `rbac.read` / `rbac.write` 只给平台 Pod 的 ServiceAccount 授权，不会自动给登记的目标集群凭据授权。

页面的只读能力预检和漂移查询按当前登录用户访问；若该用户配置了 `k8s_username`，请求会以该身份 impersonate。发布 Worker 则使用集群设置中保存的执行凭据本身。因此要分别核实“操作员能否查看目标”和“Worker 凭据能否发布”，不能因为页面能读到 Deployment 就推断蓝绿可以执行。

将 [目标集群最小权限 Role 示例](examples/delivery-target-rbac.yaml) 应用到每个实际目标 namespace，并把 RoleBinding 主体替换成 API Server 识别的执行身份。滚动发布需要 Deployment 的读取、更新和 rollout 状态读取；蓝绿另需读取 Deployment/ReplicaSet/Service/Pod/EndpointSlice/HPA/ResourceQuota，创建候选 Deployment/预览 Service，patch 稳定 Deployment 标签与 Service selector，并删除平台拥有的候选资源。该示例不授权 Secret、Pod exec、集群级资源或其他 namespace。若要进一步缩小权限，应按环境分别创建 Role/RoleBinding；候选名称动态生成，因此创建与列表权限无法通过 `resourceNames` 收窄到某一个对象。

RoleBinding 只会增加权限，不会削减该身份已有的 ClusterRole 或其他 Role 权限。生产建议为平台的执行凭据使用专用身份，并检查它没有额外绑定到集群管理员或宽泛的写入角色。

应用前用与平台中相同的执行凭据在目标 namespace 检查权限；若执行凭据是 ServiceAccount，RoleBinding 主体应使用其 namespace/name；若是 OIDC 或 token 用户，则使用集群认证层实际映射的用户名或组。当前向导会按发布 Worker 的执行凭据查询目标 namespace 权限规则，分别显示滚动与蓝绿所需写入权限；滚动还检查 Deployment 读取（SSH 模式另外检查 patch 与 rollout watch）。蓝绿计划创建时会以 Worker 身份读取目标及相关资源，读取失败同样会阻断计划。规则可读不等于准入策略、配额或后续权限变更一定允许写入，最终仍由 API Server 强制授权，真实集群仍需完成蓝绿闭环验证。

## 谁决定新镜像属于哪个组件

新镜像不会按名称猜测组件。CI 请求同时携带：

| 字段 | 示例 | 用途 |
|---|---|---|
| `target_cluster` | `test-orders` | 对应集群设置中的 env_code |
| `app_name` | `order-api` | 对应向导中的组件标识（云效全局参数 APP_NAME） |
| `image_full` | `registry.example.com/orders/api:build-42` | 对应绑定的镜像仓库和本次构建版本 |
| `image_digest` | `sha256:<64 位十六进制>` | 固化制品，防止 tag 被覆盖 |
| `event_id` | 唯一构建标识 | 同一事件重试去重 |

后端先按 `(集群, app_name)` 找绑定，再校验完整镜像仓库精确一致。
仓库的 host、端口、项目、镜像名称都要相同；相似名称、其他项目、其他 registry 会被拒绝，不产生部署任务。
同一个镜像仓库可以供多个明确标识的组件使用，CI 必须填写想更新的那个组件，平台不自动广播到所有相似组件。

`match_keyword` 只用于旧上传包的文件名匹配，不参与镜像事件路由。向导默认保留/生成该兼容字段，但不要求新用户理解它。

## 接入 CI

在**非生产、自动策略**的绑定核对页复制请求示例，替换占位符。
构建并 push 完成后，向平台公开的 `/api/v1/webhooks/yunxiao` 发送 JSON。
管理员在平台服务配置 `YUNXIAO_WEBHOOK_TOKEN`；CI 在 Secret 中保存同一密钥，通过 `X-Webhook-Token` 请求头发送。
平台页面不回显接入密钥，复制的示例不含密钥。

云效标准事件使用全局参数 `APP_NAME`、`IMAGE_FULL`、`IMAGE_DIGEST`、`TARGET_CLUSTER`；如果组件登记了非根构建目录，还需增加同值的 `SOURCE_PATH` 全局参数。为计算 Git commit 到生产的变更前置时间，可选增加 `COMMIT_TIMESTAMP`，值必须是该 `commit_id` 对应的 RFC 3339 时间（例如 `2026-10-15T09:30:00+08:00`）。缺失或格式错误不会阻断镜像接入，但该制品不能作为 DORA 变更前置时间样本；不能用流水线完成/通知时间替代。云效标准消息中的 `sources[].repo` 由流水线来源信息提供，不需要手工拼入 `globalParams`，字段见[官方消息通知文档](https://help.aliyun.com/zh/yunxiao/user-guide/message-notification)。

选择“代码仓库”时，在组件向导填写仓库地址和构建目录；`APP_NAME` 将构建绑定到这个组件。平台在创建发布单前核对 `sources[].repo` 与登记仓库。HTTPS、SSH 和 `git@host:path` 形式会按主机与仓库路径归一化，`.git` 后缀不影响匹配；多代码源中至少有一个必须匹配。登记了非根目录（如 `services/api`）时，平台还要求 `SOURCE_PATH` 与登记目录完全一致；缺少或不匹配的来源/目录会被拒绝，不会创建发布单。

发布详情并列显示接入时登记的仓库/目录和本次构建报告的仓库/目录，匹配成功时标记“仓库与目录已匹配”，有上报时也显示 Git commit 时间。自定义 Webhook 可选传入 `source_repository`、`source_repositories`、`source_path` 和 `commit_timestamp`；时间必须是 RFC 3339，缺失/无效只会使该 DORA 样本未知，不会阻断有效镜像事件。旧流水线仍可不带来源字段。同一仓库有多个服务时，每条流水线仍要设置正确的 `APP_NAME` 和 `SOURCE_PATH`。这些值由构建通知声明，不是签名证明，也不证明流水线实际 checkout 或构建的提交内容。Runner 的 Git 工作区校验针对组件登记的部署配置仓库和目录，不会自动证明代码构建来源。

## 测试和生产怎么对应

在已接入组件的列表行点击「添加环境」，自动带入组件标识、代码来源和镜像仓库，重新选择该环境的部署位置。
同一组件在不同集群使用相同 `app_name`；Deployment、namespace、容器名可以不同。
引导编辑时保持组件标识固定，避免改名后原 CI 参数指向旧组件。

测试事件只允许进入非生产自动策略集群。生产绑定不提供向生产发送自动 webhook 的示例。
测试部署成功且同 digest 的独立验收通过后，在发布中心选择生产目标、申请并由另一名操作员审批。
候选镜像必须属于生产绑定的同一镜像仓库；不匹配的目标不会作为可晋级目标，直接申请也会被拒绝。
执行前还检查组件部署位置是否被改动，避免排队后静默更新新的位置。

发布单 metadata 保存接收事件时的绑定快照，详情展示代码来源、构建目录、镜像仓库和测试部署位置。
之后编辑映射不会改写历史发布单。生产申请页显示具体 namespace / Deployment / 容器。

## 仅出网环境：云效 Runner 接入（2026-10-08，已实现）

平台和 Kubernetes 可以保持内网访问。云效 Runner 主动拉取任务，镜像推送后的通知任务在内网 Runner 上调用平台；平台按已保存的绑定更新指定容器。平台不依赖 Runner 内部控制协议，不要求外网能访问平台，也不轮询云效构建状态。

在组件列表点击「接入云效 Runner」，填写流水线 ID、私有构建集群 ID 和任务环境可访问的平台根地址。页面生成组件专属密钥、通知 Bash 脚本、云效任务 YAML、无发布副作用的接入测试脚本，以及 CI / Smoke / Scan 报告脚本。运行通知任务时，只需提供本次镜像地址和 digest；组件、环境和容器由服务端授权确定。通知返回的 `release_id` 会写入 `deploy-release-id.txt`，可用云效产物机制交给后续报告任务；Smoke 需等测试环境发布成功并通过真实探测后提交。扫描报告绑定 digest、工具及规则版本，目前仅作报告。

管理员还可配置云效连接，读取 YAML 流水线，预览追加的通知阶段，再勾选核对并保存。保存前重新读取流水线核对基线，先加密备份原始 YAML。已有阶段和任务顺序保留；无法识别的 UI 引擎格式、内容不同的同名通知阶段拒绝自动覆盖，改用生成片段手工合并。云效接口没有原子版本条件，保存时应避免其他编辑者同时修改。

专属密钥默认 90 天，只能上报该绑定的非生产自动环境及读取该绑定的发布结果。重新生成立即撤销旧密钥，禁用、到期、映射变更均阻止事件。每条流水线可为多个组件分别配置通知任务和密钥，平台不会广播更新。流水线 ID 用于匹配授权和追溯，不构成独立的构建来源证明。

通知脚本重试时保持流水线、构建编号和绑定 ID 不变，重复事件不创建第二个部署。较新构建已接收后，旧构建被拒绝，防止晚到覆盖。默认等待发布结果；202 只表示受理，rollout 成功才返回成功。页面展示接入测试时间、镜像通知和发布状态，不把历史活动显示为 Runner 当前在线。

必须在云效配置私密变量，以及推送产物的 `DEPLOY_IMAGE_FULL` / `DEPLOY_IMAGE_DIGEST` 输出。跨任务不可假设共享工作目录或环境变量；通知任务应显式取得同次构建的产物清单。真实云效、私有集群调度和镜像输出尚需现场联调；本次开发没有安装真实 Runner、保存真实云效流水线或发布 Kubernetes 镜像。

操作、接口与限制见 [Runner 接入指南](runner-integration.md)。

## 现行环境模型与发布策略（2026-10-09，已接入）

组件接入和逻辑环境配置是两个相连但不同的步骤：先在「应用与组件」登记仓库、镜像仓库和实际 Deployment/容器；保存后点击「关联业务应用与环境」，再选择业务应用、逻辑组件、逻辑环境并保存关系与策略。此保存只写平台配置，不改集群资源、不触发发布。

- `app_name` 是 CI 使用的组件标识；标准云效通知的 `APP_NAME` 必须与它完全一致。业务应用是用于归组的逻辑名称，不要把它填进 `APP_NAME`。
- 同一组件在测试、预发、生产等多个集群共用相同 `app_name`、代码来源和镜像仓库；namespace、Deployment 和容器可以因环境而不同。每个明确绑定的目标独立显示和发布，不会按相似名称广播。
- 逻辑环境与集群分开建模。环境可以关联多个集群目标；生产/非生产类型须与目标集群匹配。旧绑定会显示待核对，平台不会按名字把旧应用自动合并成业务应用或组件。
- 环境总览显示绑定目标的实际镜像、最近发布任务和观察时间；读取失败或缺少成功部署基线时显示未知与原因。镜像状态仅比较 Deployment 镜像字符串，不代表 Pod imageID、配置或业务健康。
- 滚动沿用现有 Deployment；蓝绿创建隔离候选 Deployment、预览 Service，并在人工确认后切换既有生产 Service。计划会重新核对资源 UID、入口、候选隔离和配额；外部路由、节点容量等由操作员确认。恢复稳定版后可在保留期到期时显式清理候选。
- 网关金丝雀目前只可保存为等待联调的策略草稿。已有网关的权重读写/回读和请求指标接口未确认前，不开放金丝雀审批，也不能用副本比例代替流量权重。

要接入现有网关金丝雀，请先向网关维护方确认产品/版本、平台可访问的内网地址与认证范围；路由及 stable/candidate backend 身份、当前权重读取、条件写入或幂等保护和生效回读；按路由与版本读取请求数/错误率/P95 的接口、窗口、延迟及最小样本；以及超时后的回读/重试和恢复到稳定 100% 的语义。环境策略页提供同一份可展开清单。提交脱敏 API 文档或请求/响应示例即可，勿提供 Token、密码或私钥。清单界面截图见[金丝雀网关联调资料](./visual-checks/canary-gateway-integration-checklist-390-light.png)；未完成真实联调与故障演练前，草稿仍不能审批或执行。

每次策略修改都会追加不可变版本，计划固定创建时的版本；保存环境/组件绑定本身不会触发发布。前端使用步骤引导、关系预览、固定操作区和明确的错误提示；视觉走查与剩余验收见 [发布体验规范](./release-experience-design.md)，编排和恢复边界见 [编排与环境模型](./progressive-delivery-design.md)。
