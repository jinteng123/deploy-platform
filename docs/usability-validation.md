# 发布平台可用性验证执行手册

本手册把[产品验收目标](./progressive-delivery-design.md#2-用户结果与验证)变成可复用的主持流程。它评估研发、运维和审批人能否独立理解“构建产物会更新哪里、当前发布该做什么、失败时如何恢复”，不替代真实 Kubernetes、云效或网关联调。

## 参与者与环境

邀请 5 位日常参与应用发布的真实操作者，覆盖应用研发、平台/集群运维和发布审批职责。尽量选择没参与过本平台设计或开发的人。每人单独完成一次 35–45 分钟测试；测试观察员不提示操作步骤。

只使用隔离的非生产环境和合成数据。建议准备一个 `orders-api` 组件：代码仓库 `https://git.example.com/orders.git`、构建目录 `services/api`、镜像仓库 `registry.example.com/orders/api`，并提供测试与生产两个逻辑环境及对应的 namespace/Deployment/容器。云效使用测试连接和测试流水线；所有镜像使用测试 digest。生产计划只走到待审批，不批准、不执行。暂停与恢复任务使用隔离集群中预先准备的蓝绿演练运行。不得录入真实凭据、生产 URL 或客户数据。

开始前由观察员确认测试环境可写、数据可重置、目标集群不是生产集群，通知接收端为本地测试端，恢复操作已在该环境单独演练。任一任务误选真实生产目标或出现非预期集群写入时立即停止测试并记录。

## 给参与者的任务卡

每次只给一张任务卡；不要先展示本节后半部分的判定标准。

1. **建立组件对应关系**：“订单 API 的代码已在 `orders.git`，CI 会在 `services/api` 构建 `registry.example.com/orders/api`。请把它接入平台，并指出这次构建会更新哪个环境、哪个集群里的 Deployment 和容器。”
2. **核对构建与目标**：“测试构建已经完成，平台收到了一个新的镜像 digest。请确认平台把它对应到哪个组件和目标；在你确认目标正确之前，不要发起生产变更。”
3. **查看生产发布计划**：“测试环境验证通过。请为生产环境准备发布申请，并说明候选镜像、目标工作负载、需要谁做什么，以及失败时平台准备恢复到哪里。停在待审批状态。”
4. **处理暂停中的蓝绿发布**：“一个生产发布现在暂停在业务确认前。请判断用户流量目前由哪个版本承接；如果业务检查失败，你会如何让稳定版本重新接流量，并确认恢复结果？”本任务只在隔离演练环境进行。
5. **判断金丝雀是否可用**：“团队希望按 10% 流量试运行。请检查当前环境能否安全开始，并指出仍缺少什么证据；如果不具备条件，请停在草稿或阻断状态。”

若产品当前状态无法支持某任务，记录为产品阻断，不临时口头补充能力。参与者可以使用页面内提示和文档，但观察员不解释术语或推荐按钮。

## 通过门槛与复测

- 至少 4/5 的参与者无需口头解释，就能说清 `代码仓库/目录 → 镜像仓库/digest → 组件 → 逻辑环境 → 集群/namespace/Deployment/容器`，并指出当前主行动和下一步。
- 5/5 都能识别未接通的金丝雀或未知状态为阻断，不把副本数当流量比例，不绕过审批或对真实生产执行变更。
- 至少 4/5 能在暂停演练中找到稳定版本、选择正确的恢复入口，并区分“恢复请求成功”和“稳定流量已回读确认”。
- 任何关键目标选错、越权操作或未发现的生产变更都判为失败；汇总平均值不能抵消这类失败。

未达门槛时，将每个误解映射到页面、状态文案或信息缺口，先修复最高风险问题，再用未参加过前测的操作者复测。自动化测试和截图只能证明预期状态渲染及交互，不能填入本表或代替真实参与者结果。
