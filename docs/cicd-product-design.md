## 0. 机会评估（一页纸）

- **产品定位**：基于现有 CI 的内部 Kubernetes 应用发布平台。CI 负责构建；平台负责
  制品身份、环境部署、验证证据、生产门禁、故障恢复与审计。核心价值是接入简单、
  状态可信、审批有依据、失败可恢复，不扩展为通用 CI 执行器。
- **业务目标**：把平台从"能部署"升级为"敢发布"——生产镜像与被验证的制品一致，
  同一工作负载不被并发发布覆盖，支持回滚的变更能在约定时间内恢复。
- **解决的客户问题**：运维/研发目前无法确认"测试通过的镜像"和"生产跑的字节"是同一
  份（tag 可变）；审批与并发保护尚未覆盖所有入口，失败发现与恢复仍依赖人工。
- **目标用户/画像**：
  - 发布操作者（operator 角色 / CI 系统）：要安全、可预期、出事能退。
  - 平台管理员（admin）：要审计闭环、门禁可配置。
  - 外部集成方（CI 流水线、通知机器人）：要稳定的 OpenAPI 契约。
- **关键结果（KR）**：
  - 正常生产链路 100% 使用固化的 digest；测试与生产使用相同制品身份。
  - 平台管理的同一工作负载最多一个活动发布任务；被拒绝的冲突请求单独计数。
  - 对已验证支持回滚的变更，从接受回滚任务到业务恢复的 P95 < 5 分钟；
    每月至少演练一次，记录业务检查结果。数据库不兼容变更不能承诺镜像回退即可恢复。
  - webhook 接受到测试环境部署完成 P95 < 10 分钟；验证耗时与排队耗时单独度量。
  - 分别观测部署执行失败率与上线后需要干预的变更失败率；先采集基线，再确定目标。
    原“rollout_wait 失败占比 < 10%”仅为待验证的执行质量目标，不能作为 DORA 变更失败率。

## 1. 产品原则（取舍规则）

1. **制品进入平台时固化身份**——repository + digest 标识镜像制品，tag 只是标签。
   部署/晋级/重试/回滚引用已固化身份，不能在各阶段重新解析 tag。
2. **平台不构建镜像**——构建属 CI；平台接收"已在 registry 的制品"。
   legacy 文件包路径（docker load/tag/push）逐步收口，不进新链路。
3. **部署完成与验证通过分开记录**——rollout 完成不能替代测试通过。
   当前 Deployment 更新会随副本就绪进入服务流量，生产门禁必须在更新前执行。
   “部署后再决定对用户生效”须有功能开关、蓝绿切流或渐进流量控制，按需实施。
4. **生产策略覆盖所有入口**——正常生产发布执行独立审批（SoD），审批绑定具体变更。
   旧接口、OpenAPI 与集群写入口不能绕过策略；紧急恢复采用独立授权、受限目标和审计。
5. **先证明可靠，再优化速度**——先闭合制品、门禁与恢复；门禁数量应依据实际风险验证，
   同时衡量审批等待与人工负担。
6. **发布快照支持恢复**——镜像一致不等于发布整体一致；记录配置与清单版本、迁移兼容性，
   明确镜像回退、完整回滚与向前修复的适用范围。

## 3. 发布流水线目标形态

```
CI（云效/其他）构建/测试/扫描 → push → 回调 /webhooks/yunxiao
        │  (提供 digest、构建来源、报告引用；APP_NAME 定位组件，repo/path 对照来源绑定)
        ▼
  固化镜像制品（repository + digest，不再重新解析 tag）
        │  自动 → non_production + automatic 目标；各部署独立记录
        ▼
  测试环境部署（image@sha256）→ rollout_wait → 同制品的验证证据
        │  部署成功 + 满足目标环境验证策略，才解锁晋级
        ▼
  晋级申请（operator 发起）──审批──▶ admin/第二人批准
        │  审批绑定变更快照；事务落库决定与待执行任务
        ▼
  worker 领取任务 → 工作负载互斥 → 生产部署（同制品 + 审批快照）
        │  按绑定策略：滚动 / 原生蓝绿 / 已有网关加权金丝雀
        │  持久阶段 + rollout + 业务检查 + 必要的人工确认
        │  故障 → 按兼容性回滚到已知可靠快照，或向前修复
        ▼
  通知出站 + 审计 + 生产部署/验证/故障/恢复事件入账
```

代码来源映射使用组件向导登记的仓库和仓库内目录。标准云效通知的 `sources[].repo` 必须匹配登记仓库；登记了非根目录时，流水线还需提供相同的 `SOURCE_PATH` 参数。同一单仓的多个服务通过明确的 `APP_NAME` 与目录区分，不按仓库名猜组件。来源值帮助发现配置错配，但仍是构建通知声明，不等同于签名的供应链证明。

## 4. P0 用户故事（验收标准）

### S1（F1）digest 晋级

- 作为发布操作者，我希望晋级/回滚部署的字节与 CI 产出完全一致，避免 tag 漂移。
- Given release 带 `image_digest`；When promote/rollback 执行；Then `k8s_set_image`
  使用 `repo@sha256:<digest>`，deploy_log 记录 digest。
- Given CI 提供 digest；Then 制品记录与测试部署任务在提交前固化同一身份。
- Given 兼容事件无 digest；Then 在入站时按受支持 registry 策略解析并持久化，
  标注来源为平台解析（不能宣称已证明 CI 产出一致）；无法解析则拒绝，不能延迟到晋级。
- Given 测试后 tag 被覆盖；When promote/retry/rollback；Then 仍引用原 digest。
- 观测：正常生产部署引用符合 `repo@sha256:<64 位十六进制>` 的占比 = 100%，
  制品与部署引用不一致计数 = 0；实际运行回读是额外证据，见 A1。
- 边界：暂不引入跨 registry copy；对多架构镜像区分 index digest 与平台 manifest digest。

### S2（F2）并发互斥

- Given 同实际工作负载存在 pending/running 的任务；When 任一入口再提交
  deploy/promote/rollback；Then 返回 409（`AuditConflict`），提示进行中的 log_id。
- 观测：冲突计数、并发导致的 deployment 错乱 = 0。
- 边界：建议锁粒度为 `(cluster_id, namespace, workload_kind, workload_name)`；
  同一工作负载不同容器的更新也共享锁，不同工作负载可并行。应用别名不能形成旁路。

### S3（F3）晋级审批

- Given prod 晋级请求；When 发起人提交；Then 生成 `promotion_requests{pending}`，
  不直接部署。
- When 另一名已授权该逻辑应用与生产环境的用户批准；Then 审批决定与待执行任务原子落库；发起人批准自己的
  请求 → 403。
- When 拒绝或超过 TTL；Then 状态流转并审计。
- Given 任一正常生产发布入口；Then 执行统一策略。回滚走受限的恢复规则；
  换用 API Key 不得冒充独立审批人，见 A2。
- Given 候选快照改变或当前生产基线不再匹配；Then 旧审批不能直接执行，重新验证并审批。
- Given operator 未获授权到目标逻辑应用与生产环境；When 批准或拒绝他人的申请；Then 返回 403；admin 保留全局审批权限。
- 观测：审批 P95 等待时长；未授权自审批 = 0。
- 边界：本期不做多级审批链、不接外部工单系统。

### S4（F4）任务恢复

- Given 进程重启时存在 pending/running 日志；Then `image_deploy` 重新入队幂等执行；
  `deploy`/`rollback` 标记 `interrupted`（新终态）+ 错误信息，前端可一键重试。
- 观测：重启后无永久 pending。
- 此处为当前恢复能力的验收；可靠任务闭环还须满足 A3 的故障注入、任务领取与对账标准，
  不能仅因存在 deploy_logs 就认定已具备事务 outbox。

## 5. P1/P2 摘要

- **F5 扫描门禁**：优先接收现有 CI 的扫描报告并校验 digest、来源与有效期；
  未被 CI 覆盖的扫描需求再评估平台 Trivy。先报告灰度 2 周，记录误报、未知结果与
  人工例外，再决定阻断规则；报告缺失/过期不能显示为通过。
- **F6 通知出站**：cluster/全局级出站 webhook（HMAC 签名、重试退避），事件：
  deploy_finished / promote_approved / deploy_failed / image_drift_detected / image_drift_recovered。
- **F7 发布编排**：与 F9 合并，由平台持久化阶段、动作、观察事实和恢复目标，验证暂停、
  确认、中止与恢复；`maxSurge/maxUnavailable` 不能替代流量控制。真实用户测试与视觉验收同步。
- **F8 指标**：先补齐事件与口径（A9），展示已有发布耗时/执行失败率时明确名称；
  DORA 指标依赖提交、生产变更、故障与恢复关联，不直接由 deploy_logs 推导全部指标。
- **F9 原生渐进发布**：蓝绿使用独立 Deployment 与明确绑定的 Service；金丝雀接已有
  网关权重接口。先验证候选隔离、条件切换、指标缺失与重启恢复，不要求安装 Argo CRD。
- **F10 GitOps**：本期仅在数据模型预留 `desired_state_ref`（期望状态来源标识），
  不做 reconcile。

## 6. 上线与灰度

- 每阶段功能开关：`config.features.{digest_promotion,approval_gate,scan_gate,...}`，
  默认逐环境开启（先本地/测试，再生产）。
- 每个功能上线前写预期指标变化（如"digest 部署占比 0→100%"），上线后 2 周复盘。
- 正常生产链路不得因功能开关回退而静默关闭身份与门禁校验，也不降级到可变 tag。
- 紧急例外单独定义授权人、理由、目标、有效期与审计。优先恢复已知可靠的固化快照；
  无法满足正常门禁的操作明确标注为例外，不计入“正常链路 100% 合规”。
- 未完成真实集群验收前仅限试点；具体放量条件见第 11–12 节。

## 7. 依赖与风险

- Trivy 需要可达 registry 的凭据（复用 RegistryHost 凭据配置，注意只读权限收敛）。
- 审批功能依赖用户体系完整性（disabled 用户不可审批）。
- digest 解析依赖 registry 支持 HEAD manifest（标准 v2 API，需一次 spike 验证
  用户私有 registry 兼容性）。
- F7/F9 依赖原生资源隔离、双版本容量及既有网关能力；平台承担持久编排与恢复责任。
  网关产品/API 和真实业务指标未确认前，不启用精确金丝雀。
- 单副本与内存队列是当前明确约束；先验证重启恢复和平台停机时的紧急操作流程，
  如业务确需高可用，再推进持久任务领取、数据库权威状态与多副本改造。
- 发布平台、CI、registry、监控与数据库迁移均需明确维护负责人；内部工具也有
  集成、值班与升级成本，商业可行性不能统一标为“无”。

## 9. 行业方案对照与取舍

以下保留 2026-10-05 行业对照，并于 2026-10-08 补充 Octopus/Spinnaker 的已采纳取舍。各方案处于不同层次，可组合使用；
不以功能数量作为选型依据。

| 方案 | 官方能力与做法 | 本平台差距与取舍 |
|---|---|---|
| GitLab CI/CD | 受保护环境审批、默认禁止发起人自审批；resource_group 串行部署并选择执行顺序 | 收敛所有生产入口；明确冲突重试、排队与过期任务策略，不扩展通用 CI 执行器 |
| GitHub Actions | 环境审批、禁止自审、分支/tag 限制及外部质量/变更/可观测性门禁 | 审批需绑定来源与验证证据，而非仅检查 rollout 成功 |
| Argo CD | 对比 Git 期望状态与集群实际状态、自动同步；可开启 selfHeal | 直接部署适合当前范围；漂移观测与持续对账需另行设计，GitOps 按需求决定 |
| Argo Rollouts | 金丝雀步骤、暂停、流量管理、指标分析及失败中止 | 可选外部适配；本期由平台编排原生资源与已有网关，不作为强制集群依赖 |

## 10. 开发改进项

以下均为待开发/验证项，编号用于串联风险、验收与发布检查。

### A1（P0）：入站固化制品身份

- **评审基线证据（改造前）**：`backend-go/internal/service/pipeline.go` 的 resolveDeployImage 只改变
  DeployLog.ImageFull；`service/cd.go` 的 deployImage 在 release 无 digest 时回退到
  ImageFull。测试后 tag 覆盖可导致生产再次解析为其他镜像；非配置 registry 的 tag 会跳过解析。
- **改进**：以 CI 提供 digest 为正常契约；兼容事件在入站解析并持久化，记录身份来源。
  对支持的 registry 维护明确接入规则；未知来源/解析失败拒绝进入正常生产链路。
  任务不得重新从 tag 决定制品；重放亦使用已固化引用。
- **验收**：测试部署 digest A 后覆盖 tag 为 B，生产晋级、任务重试仍为 A；
  模拟 registry 不可达、digest 不合法与外部 registry，均得到明确拒绝原因；
  重启后制品身份不丢失。对 CI 未提供 digest 的事件不宣称已证明 CI 产出一致。
- **运行证据**：image_deploy/rollback 在 rollout 后采集当前 ReplicaSet 就绪 Pod 的 imageID；蓝绿在候选完整就绪后、确认切流前采集候选 ReplicaSet 的全部期望 Pod。只有 runtime 明确暴露且与期望 digest 完全一致才标记核实。多架构时只有在配置 registry 返回的 index/manifest-list 正文摘要验证通过，且运行时 digest 出现在描述符链中才标记核实；digest 不同、runtime ID 不含 registry digest、Pod 状态读取失败均显示未知，不把未知当作通过或发布失败。蓝绿候选代码已接入；私有 registry 兼容性与真实集群验收仍待完成。
- **观测/依赖**：digest 固化失败率、正常生产 digest 覆盖率、运行偏差；依赖 registry
  凭据与多架构语义。API/DB 字段变更同步更新 `docs/openapi.yaml` 与前端契约。

### A2（P0）：统一生产策略、工作负载互斥与受限回滚

- **评审基线证据（改造前）**：`httpapi/deploy.go`、`httpapi/rollback.go` 调用 Store.AddLog，未使用
  AddDeployLog；旧部署不检查生产审批，rollback 接受任意 image_full，未验证历史目标。
  当前 CD 使用 app_name，旧部署使用 deployment_name，别名可能指向同一工作负载。
- **改进**：生产策略放在共用服务层；盘点 webhook、旧 deploy、promote、rollback、
  OpenAPI 以及 Kubernetes 写入口。正常生产镜像变更只能由授权发布任务执行；
  直接修改受管工作负载须明确拒绝或进入受审计的例外流程。
  使用实际工作负载标识互斥，覆盖同一 Deployment 不同容器的更新。
- **回滚规则**：普通回滚接收历史部署/快照 ID，由服务端确定应用、目标和镜像；
  校验属于该应用和环境、曾通过验证、制品仍可取回、配置与迁移兼容。
  任意镜像发布不能借用 rollback 名称绕过策略。
- **审批身份**：当前 OpenAPI 将 key 转为 `apikey:<name>` 用户，仅比较字符串不能证明
  两个自然人独立审批。建议机器凭据可提交申请，人工完成独立审批；如需自动审批，
  明确机器策略及凭据归属，不能记为双人审批。审批资格按应用/环境授权，而非任意 operator。
- **验收**：同工作负载通过不同入口、应用别名和容器并发提交，只接受一个活动任务，
  其余返回 409 与任务标识；无审批旧入口不能写生产；伪造回滚目标被拒；
  同一人的不同凭据不能构成双人审批；无关工作负载仍可并行。
- **观测/依赖**：冲突数、策略拒绝数、例外数与身份绕过数；依赖应用映射和身份归属。
  平台外 kubectl 操作不受进程锁控制，需集群 RBAC 与实际状态对账配合（A10）。

### A3（P0）：审批与持久任务的原子闭环

- **评审基线证据（改造前）**：`service/cd.go` 的 ApprovePromotion 先 Promote/提交 worker，再
  UpdatePromotionRequest；提交之后保存失败可能产生部署已执行而审批记录仍 pending。
  Store 内存为当前权威状态，worker 使用内存 channel，启动恢复不能替代事务执行保障。
- **改进**：数据库事务内记录审批决定、部署任务与发布关联，提交成功后再通知 worker。
  worker 从持久任务领取并有原子状态转换；单实例可先以数据库任务表实现，
  不强制引入消息队列。若使用 outbox，明确事件写入、投递确认与重复消费语义。
  审批 approve/reject/expire 使用条件状态更新，避免并发决定覆盖。
- **恢复**：逐步恢复到“先读取实际目标状态，再决定继续等待、重试或中止”；记录
  尝试次数、错误与超时。存在外部副作用时按至少一次执行设计幂等，不能承诺恰好一次。
  后续多 worker/多副本需租约与领取所有权，未验收前保持单副本约束。
- **验收**：在审批落库前、事务提交后入队前、SetImage 后状态保存前注入中断；
  未提交审批不执行，已提交任务可恢复，重复领取不产生竞争变更；审批与拒绝并发仅
  一个决定生效；数据库失败可解释，无永久 pending、无静默丢失任务。
- **观测/依赖**：任务排队/执行时长、恢复数、状态不一致数、过期活动任务数；
  依赖持久化事务接口与 worker 状态机。多副本列为后续决策，不与本期修复强制捆绑。

### A4（P1，生产放量前）：建立可晋级的验证证据

- **评审基线证据（改造前）**：validatePromotionTarget 仅检查测试 deploy_log.status=success；
  runImageDeploy 成功依据为 rollout_wait，没有独立业务验证结果。
- **改进**：分别记录部署状态、验证状态与策略结果。接收 CI 测试报告、部署后 smoke
  检查或人工业务验收，记录制品 digest、来源、时间、结果与报告引用；
  目标环境要求的证据缺失/失败/过期均不能显示为通过。
  并非全部自动要求 E2E；依据应用风险确认最低验证策略及人工例外。
- **验收**：rollout 成功但 smoke 失败仍不可晋级；其他 digest 的报告不能解锁候选版本；
  只有来源可信、有效且满足目标策略的证据才解锁。审批等待后再次检查证据有效性。
- **观测/依赖**：验证耗时、证据缺失/过期比例、阻断理由、误阻断与例外；依赖 CI 契约、
  应用负责人和检查运行方式。目标是能依据证据判断发布，而非单纯增加门禁数量。

### A5（P1）：制品、发布快照、环境部署分离

- **评审基线证据（改造前）**：ImageRelease 只有 TestClusterID/TestDeployLogID 和一组
  ProdClusterID/ProdDeployLogID；PromoteImageRelease 对已有成功生产任务整体返回冲突，
  同一制品无法正常继续晋级到第二个生产目标。
- **建议模型**：
  - 镜像制品：应用、repository、digest、CI 来源及验证证据引用。
  - 发布快照：镜像制品、部署清单/配置的版本引用、迁移兼容性与恢复方式。
  - 环境部署：快照、目标集群/环境、工作负载、任务、状态与尝试历史。
  - 审批请求：快照、目标、生产基线与策略版本；不能只有可变 release ID 的隐含语义。
- **改进**：先支持一个制品到多个独立目标的部署记录；现有表与接口迁移采用显式兼容
  方案，保留历史可追溯性。环境晋级路径是否允许 test→staging→prod 由真实需求决定。
  配置保存版本引用或 hash，不把明文 Secret 写进快照、报告或审计。
- **验收**：同制品可部署 prod-a 与 prod-b，各自成功/失败/重试不覆盖；查看历史能还原
  该次部署的制品和配置；配置改变形成新快照并重新验证。恢复前检查迁移兼容性，
  不兼容时明确引导向前修复，不提供误导性的“一键恢复”承诺。
- **观测/依赖**：各目标成功率、历史关联完整率、回滚资格覆盖率；依赖数据库迁移、
  API/前端重构与配置版本来源。复用已有 Helm/Git 版本来源，不先自研配置管理系统。

### A6（P1）：让审批成为有依据的决策

- **评审基线证据（改造前）**：release-page.tsx 已显示当前/候选镜像与审批列表，但列表主要为发布单、
  集群编号与身份状态；生产当前版本、验证证据及恢复条件尚未形成审批快照。
- **改进**：审批详情展示应用与环境名称、当前/候选版本、digest、提交、流水线名称与 ID、构建号，
  以及变更摘要、验证/扫描结果、配置变化和恢复方式。发布列表说明按平台接收顺序排列，
  构建号只在同一流水线内比较；跨分支或流水线通过 Commit 与镜像 digest 核对制品。明确区分“申请发布”“审批通过”
  “等待执行”“部署完成”“验证通过”，按钮与返回状态一致。
- **过期与并发变更**：TTL 只是时间限制。若候选快照、策略或生产基线改变，执行前
  重新校验并使原审批失效；旧版本默认不能作为普通前向发布覆盖新版本，
  合法回退使用明确的恢复流程。采用可比较的部署版本标识，不仅靠镜像字符串。
- **验收**：5 位真实操作者完成申请、拒绝、故障定位与恢复；至少 4 位不需引导即可
  判断候选内容、阻断原因和恢复方式（试点目标，按测试结果调整）。基线改变后的旧审批
  不执行，页面解释原因；同一请求重复点击不重复部署。
- **观测/依赖**：审批等待 P95、操作错误、任务完成率与人工求助次数；依赖 A1/A4/A5。

### A7（已采纳，分阶段试点）：原生渐进发布与部署/生效解耦

- **问题**：普通 Deployment 的 maxSurge/maxUnavailable 控制滚动过程中的副本数量，
  不单独保证精确批次、批间验证与流量比例。平台轮询后临时 pause 存在控制时序风险。
- **改进**：保留 Deployment 和云效构建，由平台管理环境绑定、不可变计划、审批、阶段、
  进度与恢复。逻辑环境跨组件复用，具体环境目标显式绑定集群、namespace、Deployment、容器和入口；同一 digest 按环境逐步晋级。蓝绿通过新旧 Deployment 与 Service selector 切换；金丝雀接已有网关权重 API，并要求配置生效回读及按 digest 区分的真实指标。
  借鉴 Octopus 接入/环境模型与 Spinnaker 编排，不要求 Argo CRD。完整契约见
  [原生编排设计](./progressive-delivery-design.md)。
- **验收**：候选提前接流量防护、切流条件更新、人工确认、指标失败恢复、缺失指标暂停、
  写入响应丢失和平台重启回读均可复现；已配置权重与实际请求分开展示，恢复有业务检查。
- **范围**：先支持明确入口的无状态 HTTP 服务和固定策略模板；普通滚动审批仍在更新前。
  HPA、独占卷、队列消费者、多入口/多组件事务与多实例执行安全不纳入首期承诺。
- **前端**：引导、环境、计划/审批、阶段现场和恢复页同步交付，统一视觉 tokens、留白、
  状态与行动层级；截图、深色/窄屏与可用性验收是放量条件，见 [体验规范](./release-experience-design.md)。
- **观测/依赖**：双版本容量、入口切换/生效、请求分布、版本指标、恢复耗时、操作负担。
  蓝绿按 D1–D4 推进，金丝雀依赖 G1 网关真实联调与 G2 试点，不用副本比例兜底冒充精确流量。

### A8（P1）：通知与扫描的可靠集成

- **扫描**：优先复用 CI 扫描，绑定 digest、工具/规则版本与报告时间；Runner 已有组件专属上报接口和接入引导脚本，发布详情展示报告元数据；当前保持只报告，灰度观察至少两周后再评估是否设门禁。
  明确 critical 阻断、修复可用性、误报例外、例外期限与未知结果策略。
  只有 CI 覆盖不足且确有需求时，再承担平台异步 Trivy 与凭据维护。
- **通知**：失败通知包含应用、环境、任务链接、失败步骤和下一步；成功/审批事件按需。
  通知使用持久投递记录、事件 ID、签名、退避与次数上限，投递失败可见且可重试。
  外部接收方按事件 ID 去重；通知故障不能改变部署事实。
- **验收**：CI 旧报告/不同 digest/无报告不会显示扫描通过；报告灰度不阻断。
  通知目标超时/返回错误可重试，重启不丢投递记录，不泄漏凭据。
- **观测/依赖**：误阻断率、报告覆盖率、投递成功率与延迟；依赖 A3/A4 与通知负责人。

### A9（P1 采集 / P2 展示）：修正指标口径

当前 DORA 官方采用五项指标；本平台应按应用/服务统计，避免跨不同业务混合排行。

| 指标 | 口径 | 所需新增或确认的数据 |
|---|---|---|
| Change lead time | 代码提交进入版本控制到生产部署的时间 | Git 提交时间、提交集合与生产部署关联；构建时间不能代替提交时间 |
| Deployment frequency | 指定应用生产部署次数/时间区间，或部署间隔 | 生产部署事件；按服务定义多集群一次发布的去重口径 |
| Failed deployment recovery time | 失败部署需要干预到恢复的时间 | 故障/干预起点、关联部署与业务恢复确认；不只统计回滚任务执行时间 |
| Change fail rate | 需要立即干预的生产部署 / 生产部署总数 | 回滚、热修复或事件关联；rollout 成功后发生故障也计入 |
| Deployment rework rate | 因生产事件导致的非计划部署 / 生产部署总数 | 是否计划内、关联事件、修复类型 |

- 先记录 release/deployment/verification/incident/recovery 的稳定关联 ID 与时间。
  同时提供平台执行指标：入站固化失败、排队、rollout、验证、审批等待、通知投递与恢复耗时。
- 缺少提交或事件关联时显示未知/覆盖率，不填 0，不将“构建→生产耗时”命名为 DORA lead time。
- **验收**：用一组包含正常部署、rollout 失败、上线后故障、回滚与热修复的固定事件，
  手工核对统计；可从聚合值追溯事件，时间起点和分母明确。
- **观测/依赖**：数据关联完整率、指标使用者与实际决策；依赖 CI/Git/事件记录。
  先有基线与使用场景，再投入完整面板，不把指标排名当产品目标。

## 17. 组件配置来源的可理解绑定（2026-10-14）

接入体验将组件与三类对象分开展示：源码仓库和源码目录、部署配置仓库和配置目录、镜像仓库与 Kubernetes 目标。部署配置仓库是组件绑定的可选默认值；Runner 对其固定仓库/目录，只让每次构建提交配置 commit，从而把镜像构建和部署配置版本放到同一制品及审批计划上核对。未登记默认仓库时，旧版按构建传入来源的方式保持兼容。

这减少重复填写并降低错误对应风险，但不代表平台能证明 CI checkout 或配置应用结果。CI 仍执行实际 checkout/渲染/应用；平台仅固定声明并在默认来源缺 revision 时阻断审批计划。恢复历史配置、校验 Helm 渲染和评估数据库变更兼容性仍是 A5 后续工作，见[组件接入文档](./component-onboarding.md)和 [ADR-0002](./adr/0002-component-deployment-config-source.md)。
